# Adopting the perf fixes in dist/

Everything below is one patch, `sandbox/perf/adopt.patch`, generated by `python sandbox/perf/make_adopt.py` from exact
anchors in the CURRENT `dist/`: **main 8d21618** as merged into `claude/raft-tech` (game.js 2284 lines, build stamp
`v3-survival-ae77fa84ac2b`). Every anchor quoted here occurs exactly once in its file; `make_adopt.py` refuses to write
the patch otherwise, and `git apply --check sandbox/perf/adopt.patch` passes. `make_adopt.py --steps 1,3` builds a
patch with only some steps. Line numbers refer to the unpatched files. Steps are independent of each other.

What main already does from the perf studies, so it is not in this patch: floating supplies cast no shadow
(`syncItems`), the sun's shadow box is fitted to the raft (`fitShadow`), the far islands and clouds are baked, the deck
is merged across tiles (deck.js `createRaftMesh`), `renderer.info` is reset by hand so it counts the shadow pass,
quality.js does dynamic resolution and shadow-map steps, and (new in 8d21618) **wood.js has no bump map any more**,
which was this study's step 4 against the previous base. The status of each finding is in `docs/tech/perf.md`.

## 1. Incremental raft rebuild (game.js lines 10, 606-623, 2216; live.js line 22)

**Why.** `rebuildRaft()` runs on every floor and decoration built, every synced world change (guest), every repaint
of a deck tile, every save load and every hot swap. It disposes and regenerates **every** deck tile (`createRaftMesh`
extrudes each plank) and **every** decoration model (`createCraft`: a sail is 67k vertices and ~46 ms, a net 53k, a
crate 31k). `node sandbox/perf/floorcost.mjs` on this base (process CPU time, loaded box, roughly 2x a quiet machine):
the deck costs 53 ms at 9 tiles, 183 ms at 25 and 319 ms at 49; the 12 decorations of the test raft 183-253 ms more.
Patched, one new tile costs 10-19 ms and a decoration costs no deck work. In the game (`playtest.py --big`, previous
base) the click handlers went from 0.5-7.6 s to 0.02-0.8 s headless.

**What.** deck-cache.js keeps each tile's generated geometry (CPU only, never uploaded) keyed by tile and, when the
paint lane tints the deck, by the tile's tint (`tint(t, '#bb8a53')`, a real plank shade), generates only new or
repainted tiles and concatenates per material; with an unchanged key list it returns the same group, so placing a
decoration costs no deck work. A decoration whose save entry (`JSON.stringify(d)`) is unchanged keeps its model.
Cost: the cached tile geometry doubles the deck's JS memory (+0.3 MB per tile; 14.8 MB at 49 tiles). GPU memory is
unchanged.

Why reuse is safe with the modules that touch decor models (checked in the code and in the playtest):
- **sailing-world.js** `onRaftBuilt()` calls `restoreSails()` first (resets cloth scale/position, removes its furl
  roll) and then re-finds sails among `raft.children`, so a kept sail is re-adopted exactly like a new one.
- **watering** (palms, purifiers, rain barrels, sprinklers): kept models are re-registered in `wateringGroups` from
  their `userData.tileKey`; `preparePlanter` already ran on kept palms and is idempotent anyway.
- **daynight.js** rescans lanterns when the raft's child count or first child changes, and every 0.5 s checks that its
  lanterns still have the raft as parent, so added and removed lanterns are picked up as before.
- **paint.js** asks for a rebuild when the set of painted tiles changes; the repainted tiles get new cache keys, and
  `content.afterRebuild()` still runs after every rebuild (it re-tints building pieces).
- **progression-hooks.js** `modelFor` registers cooker models by `keyOf(d)`; a kept model stays registered, a changed
  entry builds and registers a new one. Every model factory (`createCraft`, `createSignalModel`, `createPurifier`,
  `createRainBarrel`, `createSprinkler`, `content.decorModel(type, d)`, `prog.modelFor(type, d)`) depends only on the
  type and the entry `d`, which is the reuse key, so a kept model is what a rebuild would make. The playtest compares
  every decoration's geometry after incremental builds with a hot swap's fresh rebuild
  (`incrementalDecorEqualsFullRebuild`).
- A guest receiving a host world with different tiles gets a rebuilt deck (tiles that left are evicted).

## 3. live.js: two overlapping update checks mount two engines (live.js line 265)

**The race.** `check()` tests `state.updating` before `await fetchManifest()`, but only `swap()` sets it. Two checks
that overlap (the 6 s poll and a `visibilitychange` `schedule(0)`, or the poll and a manual `raftLive.check()`) both
pass the guard, both await the manifest, and both call `swap()` from the same old engine. The second swap captures and
disposes the old engine again and mounts a third; the engine mounted by the first swap is never disposed and keeps its
`requestAnimationFrame` loop rendering into the shared canvas (an orphaned engine: it renders every frame on top of the
live one; the first perf study counted +170 geometries and +8 textures per occurrence).
`python sandbox/perf/live_race.py` reproduces it: two concurrent checks return `["updated", "updated"]` and leave
**2** `animate` loops running. (`tests/audit/live3_concurrent_checks_double_swap.py` tests the same contract but times
out before testing: it clicks `#solo` with a Playwright locator, and the title menu hides that button.)

**The fix: one line.** Re-test the guard after the await. Whichever check resumes first calls `swap()`, which sets
`state.updating = true` synchronously before its first await, so the later one returns `busy`:

```js
  try {
    manifest = await fetchManifest();
    if (state.updating) return { status: 'busy', build: state.build }; // another check() started a swap while this one waited
  } catch (e) {
```

Insert after line 265, the `manifest = await fetchManifest();` inside `check()` (line 234 has the same text inside
`boot()`, so anchor on the following `} catch (e) {` / `// Silent: network hiccups must not disturb play.`). If the
first swap already finished, the later check sees the new `state.build` and returns `current`; if it failed, it
returns `failed-recently`. Patched: `["updated", "busy"]`, **1** render loop.

## 4. The `low` preset also turns MSAA off (game.js lines 9, 46, 437)

**Why.** The renderer asks for MSAA whenever `devicePixelRatio < 1.5`. On SwiftShader that is the largest single
raster cost found: the same frozen frame without MSAA costs **-35%** GPU-process CPU (1127 -> 729 ms, previous base;
-47% together with the bump map that main has since dropped). On real hardware MSAA is much cheaper, but weak
integrated GPUs at 1080p feel it too. quality.js cannot change it at run time (it is a context attribute), so this ties
it to the player's saved preset: `low` (pixel ratio 1, no shadows) now also means no MSAA, applied when the context is
created, i.e. from the next page load. Hot swaps reuse the renderer and never change it mid-session. 2.4% of pixels
change (geometry edges).

```js
// line 9
import { createSettings, SETTINGS_DEFAULTS, SETTINGS_STORAGE_KEY, validateSettings } from './settings.js?build=v3-survival-ae77fa84ac2b';
// after line 46 (const PIN_QUALITY = ...)
const storedGraphics = () => { try { return validateSettings(JSON.parse(localStorage.getItem(SETTINGS_STORAGE_KEY))).graphics; } catch { return null; } }; // perf: the saved preset, before createSettings() runs
// line 437: antialias:devicePixelRatio < 1.5 becomes
new T.WebGLRenderer({canvas, antialias:devicePixelRatio < 1.5 && storedGraphics() !== 'low'}); // dense screens get their smoothing from pixels, not MSAA; 'low' skips MSAA (~1/3 of software-GL raster; applies from the next load)
```

`createSettings()` only applies the saved preset after `init()`, which is why the preset is read from storage here.
A settings hint such as "Low also turns off anti-aliasing after a reload" would be a ui-feel call.

## Measured, not adopted

- **Lantern pool lights out of the scene by day** (daynight.js keeps 1-4 point lights in the scene at intensity 0 once
  a lantern exists): -7% raster on the 49-tile raft by day (that pose's run-to-run noise is +7%) and -6% at night
  (noise +2%). It would break daynight's explicit contract (tests/daynight.test.mjs `P2-1: ... never toggled by
  time`). A proposal for the daynight owner, not a patch: three keeps every program variant per material, so it can be
  done without a dusk shader hitch.
- **512 shadow map**: 0% at spawn, inside noise on the big raft; quality.js already drops to 512 on its lower levels.
- **Shadows off**: -1% at spawn (nothing visible is shadowed there), -5% on the big raft; already a setting and the
  last quality level.
- **Content island, wildlife, sailing, night, underwater**: no cost worth a change (perf.md "Poses").

   `git apply --check sandbox/perf/adopt.patch`.
2. `node --test sandbox/perf/deck-cache.test.mjs` (4 pass) and `node sandbox/perf/floorcost.mjs` (rebuild CPU: stock

3. `python sandbox/perf/verify_adopt.py` applies the patch to a temp copy of `dist/` and runs, stock vs patched: the
   frozen-scene profile at spawn on the 9-tile and 49-tile rafts with pixel diffs (READ the PNGs it writes),
   `node --test tests/*.test.mjs` (incl. live-preload and module-specifier checks), the budgeted perf gate
   `tests/e2e/perf_gate.py`, `live_race.py` and the hot-swap leak audit, and `playtest.py --big` (hammer floors,
   decorations, hook, two hot swaps through live.js's own poll; `incrementalDeckEqualsFullRebuild` and
   `incrementalDecorEqualsFullRebuild` must be true, memory flat across swaps). `--skip shoot,node,gate,audit,play`
   runs a subset. The audits run from copies of `tests/` in which `page.locator('#solo').click(...)` is replaced by a
   JS click (they time out on the current title screen otherwise).
4. In a browser: `dist/index.html?perf` (or F3). Build a floor and place a decoration on a big raft: no hitch, and the
   panel's geometry count changes by one tile's or one model's worth. Paint a deck tile: only that tile changes. Set
   the preset to Low, reload: edges alias, the panel reads `low 1/..: pr 1, no shadows`.
