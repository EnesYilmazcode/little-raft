# Adopting the perf fixes in dist/

Everything below is one patch, `sandbox/perf/adopt.patch`, generated by `python sandbox/perf/make_adopt.py` from exact
anchors in the CURRENT `dist/` (game.js build `v3-survival-ae77fa84ac2b`, 1780 lines, branch `claude/raft-tech`).
Every anchor quoted here occurs exactly once in its file; `make_adopt.py` refuses to write the patch otherwise, and
`git apply --check sandbox/perf/adopt.patch` passes. `make_adopt.py --steps 1,3` builds a patch with only some steps.
Line numbers refer to the unpatched files. Steps are independent of each other.

What main already does from the first perf study, so it is not in this patch: floating supplies cast no shadow
(`syncItems`), the sun's shadow box is fitted to the raft (`fitShadow`), the 12 islands and 24 clouds are baked
(`bakeGroup`/`mergeStatic`), the deck is merged across tiles (deck.js `createRaftMesh`), `renderer.info` is reset by
hand so it counts the shadow pass, and quality.js does dynamic resolution and shadow-map steps. The status of each old
finding is in `docs/tech/perf.md`, "Old findings, now".

| step | files | what | measured gain | looks |
|---|---|---|---|---|
| 1 | new `dist/deck-cache.js`, game.js | incremental `rebuildRaft()`: tiles generated once, unchanged decor keeps its model | a build on a 49-tile raft with 12 decorations: ~510 ms of CPU becomes ~35 ms (one tile) or ~0-46 ms (one model) | identical (vertex checksums) |
| 2 | new `dist/perf-overlay.js`, game.js | F3 / `?perf` panel reading quality.js | none (hidden: 2 `performance.now()` per frame) | panel only when asked |

## 1. Incremental raft rebuild (game.js lines 41, 491-507, 1720)

**Why.** `rebuildRaft()` runs on every floor and decoration built, every synced world change (guest), every save load
and every hot swap. It disposes and regenerates **every** deck tile (`createRaftMesh` extrudes each plank) and
**every** decoration model (`createCraft`: a sail is 67k vertices and ~46 ms, a net 53k, a crate 31k). Measured with
`node sandbox/perf/floorcost.mjs` (process CPU time, load average ~40, so roughly 2x a quiet machine): the deck costs
57 ms at 9 tiles and 309 ms at 49; the 12 decorations of the 49-tile test raft cost 205 ms more. In the game,
`playtest.py --big` (5x5 raft, 8 decorations) timed the click handlers: stock floor clicks 545-2995 ms, decoration
clicks 462-7565 ms; patched 61-630 ms and 24-795 ms (wall clock on the loaded box: compare the two, not the values).

**What.** deck-cache.js keeps each tile's generated geometry (CPU only, never uploaded) keyed by tile, generates only
new tiles and concatenates per material; with an unchanged tile list it returns the same group, so placing a
decoration costs no deck work. A decoration whose save entry (`JSON.stringify(d)`) is unchanged keeps its model.
Cost: the cached tile geometry doubles the deck's JS memory (+0.3 MB per tile; 14.8 MB at 49 tiles). GPU memory is
unchanged.

Line 41, after `import { mergeGeometries } from './merge-geo.js?build=v3-survival-ae77fa84ac2b';` add:

```js

```

Why reuse is safe with the modules that touch decor models (checked in the code and in the playtest):
- **sailing-world.js** `onRaftBuilt()` calls `restoreSails()` first (resets cloth scale/position, removes its furl
  roll) and then re-finds sails among `raft.children`, so a kept sail is re-adopted exactly like a new one.
- **watering**: kept palms and purifiers are re-registered in `wateringGroups` (their `userData.tileKey` stays);
  `preparePlanter` already ran on them and is idempotent anyway.
- **daynight.js** rescans lanterns when the raft's child count or first child changes, and every 0.5 s checks that its
  lanterns still have the raft as parent, so added and removed lanterns are picked up as before.
- **progression-hooks.js** `modelFor` registers cooker models by `keyOf(d)`; a kept model stays registered, and a
  changed entry builds and registers a new one. Every model factory (`createCraft`, `createSignalModel`,
  `createPurifier`, `content.decorModel`, `prog.modelFor`) depends only on the type, so a kept model is what a rebuild
  would make. The playtest compares every decoration's geometry after incremental builds with a hot swap's fresh
  rebuild (`incrementalDecorEqualsFullRebuild`).
- A guest receiving a host world with different tiles gets a rebuilt deck (tiles that left are evicted from the cache).

## 3. live.js: two overlapping update checks mount two engines (live.js line 221)

**The race.** `check()` tests `state.updating` before `await fetchManifest()`, but only `swap()` sets it. Two checks
that overlap (the 6 s poll and a `visibilitychange` `schedule(0)`, or the poll and a manual `raftLive.check()`) both
pass the guard, both await the manifest, and both call `swap()` from the same old engine. The second swap captures and
disposes the old engine again and mounts a third; the engine mounted by the first swap is never disposed and keeps its
`requestAnimationFrame` loop rendering into the shared canvas (an orphaned engine: it renders
every frame on top of the live one; the first perf study counted +170 geometries and +8 textures per occurrence). `python sandbox/perf/live_race.py` reproduces it on stock: two concurrent checks return
`["updated", "updated"]` and leave **2** `animate` loops running. (`tests/audit/live3_concurrent_checks_double_swap.py`
tests the same contract but times out before testing: it clicks `#solo` with a Playwright locator, and the onboarding
title menu now hides that button.)

**The fix: one line.** Re-test the guard after the await. Whichever check resumes first calls `swap()`, which sets
`state.updating = true` synchronously before its first await, so the later one returns `busy`:

```js
  try {
    manifest = await fetchManifest();
    if (state.updating) return { status: 'busy', build: state.build }; // another check() started a swap while this one waited
  } catch (e) {
```

(Insert after line 221, the `manifest = await fetchManifest();` inside `check()`; line 191 has the same text inside
`boot()`, so anchor on the following `} catch (e) {` / `// Silent: network hiccups must not disturb play.`.) If the
first swap already finished, the later check sees the new `state.build` and returns `current`; if it failed, it returns
`failed-recently`. Patched: `["updated", "busy"]`, **1** render loop.

## 4. Drop the plank bump map (wood.js lines 16-19)

**Why.** 892db6d made the bump term sample an isotropic twin of the colour map (about -15%). The bump is still
invisible at `bumpScale .018`: with and without it the frozen-scene screenshots differ by 0.01 (0-255) on the deck and
no pixel by more than 8/255. Its three extra texture taps per deck pixel still cost -14% of SwiftShader raster at spawn,
-11% on the 49-tile raft and -18% once MSAA is off. It also frees one texture per timber colour (15 -> 8 live
textures at spawn). building-models.js (`createPieceMaterial`) already handles a material without `bumpMap`
(`for (const t of [m.map, m.bumpMap]) if (t)`).

Replace lines 16-19:

```js
 // The bump term samples its map three times per pixel; anisotropic filtering there is invisible at this bump
 // scale but costly on software GL, so the bump reads the same canvas through an isotropic twin.
 const bump=texture.clone();bump.anisotropy=1;
 return new T.MeshStandardMaterial({map:texture,bumpMap:bump,bumpScale:.018,roughness:.86,metalness:0});
```

with

```js
 // No bump map: at bumpScale .018 it changed no pixel by more than 8/255 (deck diff 0.01 of 255), but even through
 // an isotropic twin its three extra taps per pixel were 11-18% of a SwiftShader frame (docs/tech/perf.md).
 return new T.MeshStandardMaterial({map:texture,roughness:.86,metalness:0});
```

If art later wants visible grain relief, that means raising `bumpScale`, which is a look change and an art call.

## 5. The `low` preset also turns MSAA off (game.js lines 8, 40, 378)

**Why.** The renderer asks for MSAA whenever `devicePixelRatio < 1.5`. On SwiftShader that is the largest single
raster cost found: the same frozen frame without MSAA costs **-35%** GPU-process CPU (1127 -> 729 ms), and -47%
together with step 4. On real hardware MSAA is much cheaper, but weak integrated GPUs at 1080p feel it too.
quality.js cannot change it at run time (it is a context attribute), so this ties it to the player's saved preset:
`low` (pixel ratio 1, no shadows) now also means no MSAA, applied when the context is created, i.e. from the next page
load. Hot swaps reuse the renderer, so they never change it mid-session. 2.4% of pixels change (geometry edges).

```js
// line 8
import { createSettings, SETTINGS_DEFAULTS, SETTINGS_STORAGE_KEY, validateSettings } from './settings.js?build=v3-survival-ae77fa84ac2b';
// after line 40 (const PIN_QUALITY = ...)
const storedGraphics = () => { try { return validateSettings(JSON.parse(localStorage.getItem(SETTINGS_STORAGE_KEY))).graphics; } catch { return null; } }; // perf: the saved preset, before createSettings() runs
// line 378: antialias:devicePixelRatio < 1.5 becomes
new T.WebGLRenderer({canvas, antialias:devicePixelRatio < 1.5 && storedGraphics() !== 'low'}); // dense screens get their smoothing from pixels, not MSAA; 'low' skips MSAA (~1/3 of software-GL raster; applies from the next load)
```

`createSettings()` only applies the saved preset after `init()`, which is why the preset is read from storage here.
A settings hint such as "Low also turns off anti-aliasing after a reload" would be a ui-feel call.

## Measured, not adopted

- **Lantern pool lights out of the scene by day** (daynight.js keeps 1-4 point lights in the scene at intensity 0 once
  a lantern exists): -6 to -7% raster on the 49-tile raft, which is inside that pose's run-to-run noise (baseline vs
  baseline-2: +7%). It would also break daynight's explicit contract (tests/daynight.test.mjs `P2-1: ... never toggled
  by time`). Not worth it at this evidence; three keeps every program variant per material, so it could be done
  without a dusk hitch if a quieter machine shows a real gain.
- **512 shadow map**: 0% at spawn, inside noise on the big raft; quality.js already drops to 512 on its lower levels.
- **Shadows off**: -1% at spawn (nothing visible is shadowed there), -5% on the big raft; already a setting and the
  last quality level.
- **Content island, wildlife, sailing, night, underwater**: no cost worth a change (perf.md "Poses").

## How to verify

1. `python sandbox/perf/make_adopt.py` (regenerates the patch and asserts every anchor), then
   `git apply --check sandbox/perf/adopt.patch`.
2. `node --test sandbox/perf/deck-cache.test.mjs` (3 pass) and `node sandbox/perf/floorcost.mjs` (rebuild CPU: stock
   deck vs one new tile, `sameGeometry: true`).
3. `python sandbox/perf/verify_adopt.py` applies the patch to a temp copy of `dist/` and runs, stock vs patched: the
   frozen-scene profile at spawn on the 9-tile and 49-tile rafts with pixel diffs (READ the PNGs it writes),
   `node --test tests/*.test.mjs`, the budgeted perf gate `tests/e2e/perf_gate.py`, `live_race.py` and the hot-swap leak
   audit, and `playtest.py --big` (hammer floors, decorations, hook, two hot swaps through live.js's own poll;
   `incrementalDeckEqualsFullRebuild` and `incrementalDecorEqualsFullRebuild` must be true, memory flat across swaps).
   `--skip shoot,node,gate,audit,play` runs a subset. The gate and the audits run from copies of `tests/` in which the
   `page.locator('#solo').click(...)` boot step is replaced by a JS click (they time out on the current title screen
   otherwise; see perf.md).
4. In a browser: `dist/index.html?perf` (or F3). Build a floor and place a decoration on a big raft: no hitch, and the
   panel's geometry count changes by one tile's or one model's worth. Set the preset to Low, reload: edges alias, the
   panel reads `low 1/..: pr 1, no shadows`.
